### Candidate acceptance

Lifecycle: PENDING_VALIDATION → ACTIVE → AUTHORIZATION_REQUIRED, SUPERSEDED or REVOKED as applicable. Code exchange alone is not acceptance. After exchange subject/scope checks and encryption, a separate server-only candidate record is PENDING_VALIDATION with a ten-minute acceptance expiry; it is never the continuity pointer and cannot execute. Callback decrypts through the existing authenticated credential lifecycle and invokes the exact same refreshProof/provider.refresh authority used by access(). The real provider checks OAuth audience, access-token presence and current Google subject; shared proof checks binding subject/scopes and records optional Script availability.

Fresh canonical principal, immutable Project/Spreadsheet/subject/revision and consent authorizationVersion/previous-pointer checks precede atomic promotion. Only then does new become ACTIVE, old same-Project grant become SUPERSEDED with its secret removed, and continuity become CONNECTED pointing at new. Failed candidate validation deletes the candidate, preserves old grant/continuity exactly and emits only bounded GOOGLE_AUTH_VALIDATION_FAILED audit details. A process crash can leave an expired noncanonical PENDING_VALIDATION record; expiry forbids activation and ACTIVE-only discovery excludes it. No new TTL/deletion deployment is claimed. Local preservation does not promise Google will never revoke an old token independently.

Revocation increments authorizationVersion even before first activation, fencing in-flight consent. Concurrent callbacks cannot replace a grant accepted after their consent began. A lost activation acknowledgment can be recovered from the already committed, validated canonical grant without another consent. Refresh re-reads canonical pointer, status and binding after external I/O and preserves existing execution/request/acknowledgment fences. No grant in another Project may be superseded/revoked by a corrupted local pointer.

### Reasons and safe diagnosis

Authoritative audit/state reasons: AUTH_GRANT_MISSING, AUTH_GRANT_NOT_ACTIVE, AUTH_ACTOR_MISMATCH, AUTH_PROJECT_MISMATCH, AUTH_SUBJECT_MISMATCH, AUTH_SPREADSHEET_MISMATCH, AUTH_BINDING_REVISION_MISMATCH, AUTH_PROVIDER_SUBJECT_CHANGED, AUTH_REFRESH_REJECTED, AUTH_REFRESH_SUBJECT_MISMATCH, AUTH_BINDING_SCOPE_MISSING and AUTH_AUTOMATION_SCOPE_MISSING. Access can return public AUTHORIZATION_REQUIRED while retaining the specific bounded reason in authoritative diagnosis/audit. A different administrator's actor-mismatch attempt is denied/audited without disabling the owner's grant. Invalid refresh/subject/binding scopes invalidate the applicable local grant. Foreign-Project grant data is never modified by this failure path.

GOOGLE_SERVICE_UNAVAILABLE, GOOGLE_NETWORK_ERROR, GOOGLE_RATE_LIMITED and GOOGLE_QUOTA_EXCEEDED keep the grant ACTIVE and continuity CONNECTED; they return their original canonical code. Successful retry clears transient diagnosis. Missing optional Script scope records automationAuthorized=false while preserving binding/sync; explicit Apps Script consent is separate. Local decryption/configuration failure is not proof that Google rejected the credential.

`diagnoseWorkspaceAuthorization(projectId,user)` reads only authorized metadata and current Firebase provider identity. It never decrypts, reads OAuth configuration or invokes Google refresh. Closed results: CONNECTED_VALID, REAUTHORIZATION_REQUIRED, GRANT_BINDING_STALE, ACCOUNT_MISMATCH, AUTOMATION_SCOPE_REQUIRED, PROVIDER_TEMPORARILY_UNAVAILABLE, with optional allowlisted reason/providerCode and metadataOnly=true. CONNECTED_VALID describes stored/current binding metadata, not a fresh live Google-health check. No credential, email, Google subject ID or raw provider payload is returned. GET Workspace status includes this diagnosis; a protected no-store GET authorization/diagnosis also exposes it. The UI requests reauthorization only for credential invalidation, review for binding/account mismatch, a separate Script grant for automation-only scope and retry for temporary service failure. Failed replacement surfaces a bounded callback code/reason without claiming success or overwriting old state.

# Implemented Workspace background authorization and delivery

## Trust and credential boundaries

`workspaceGoogleOfflineAuthorization.server.ts` owns start/callback/refresh/revocation. `workspaceGoogleOffline.adapter.ts` performs Google code/token protocol. The normal Firebase login is unchanged. A current Project administrator starts a 10-minute, browser-cookie-bound, single-use PKCE S256/state/nonce transaction. Callback rechecks current Project authority, immutable binding/revision, Google subject against the Firebase provider account and binding, ID-token issuer/audience/nonce, and required Sheets/drive.file grants. Optional Script scope is requested only for automation; declining it does not discard a usable binding/sync grant or weaken the separate Script installer check.

The exact server-configured callback is used for the authorization URL and code exchange. Transaction consumption happens before external exchange; a failed exchange needs fresh consent rather than replay. An HttpOnly/Secure/SameSite=Lax cookie and state hash bind the callback to its originating browser. PKCE verifier is encrypted in the short-lived server transaction. A CSP-restricted completion page sends only Project ID/result or closed failure code/reason to the exact configured opener origin; the client additionally checks message origin, popup source and current Project/account intent. No token/code/state/provider identity is reflected into the completion page. Callback query strings must also be excluded from hosting/proxy access logs; the application never logs them.

Server-only root collections `workspace_google_oauth_transactions` and `workspace_google_authorizations` are covered by existing Firestore default-deny client rules, including for administrators. No browser rule grants access. Refresh credentials are AES-256-GCM ciphertext with random 96-bit nonce, authentication tag and key version; AAD binds Project, Google subject and authorization ID. Raw access tokens are transient server memory. Credential ciphertext is not stored in Project business documents. Continuity stores only the non-secret authorization pointer/status. No refresh credential reaches a browser or application API DTO. API output/logs contain no raw provider payload.

After shared first-refresh proof, reauthorization atomically supersedes/removes the previous same-Project local secret and installs the validated canonical grant, without changing the Sheet or Google subject. Refresh verifies audience, current subject and required scopes. Revoked/invalid grants become AUTHORIZATION_REQUIRED while binding remains CONNECTED. Transient refresh/provider errors preserve active grant and pending work with degraded sync. Explicit revoke deletes local usable credential material before best-effort Google revocation, even if Google/configuration is unavailable. Existing type/lint debt is not waived.

## One worker and one delivery authority

`server/workspaceSyncWorker.ts` delegates to WorkspaceSyncCoordinator, shared with the global user-active endpoint. Actor passes discover owned history/filter ACTIVE, require actual pending work and use pending-only retrySync without maintenance. Dormant scheduled passes discover ACTIVE grants and retain the separately permitted initializeBound/retrySync policy. Both revalidate canonical grant pointers, ownership and current principal/Project authority, with bounded paging/pass ownership and existing Project leases. No scheduler is started. The same canonical snapshot, RAW writer, operational event contract and acknowledgment path serve browser-triggered and unattended requests. No parallel engine, business database or Sheet-to-Firestore ingestion is added.

A Project lease records owner, claim time, expiry and binding revision. It renews every 30 seconds, expires after 120 seconds and fences every provider HTTP request and acknowledgment. A worker cannot reclaim an unexpired owner. Legacy owners lacking expiry first receive a 120-second quarantine expiry. Current principal, canonical active grant, Project/binding/subject and lease/revision are revalidated; revocation or replacement prevents acknowledgment. All provider requests use 15-second timeouts and no hidden retries. An already-in-flight Google mutation cannot participate in a Firestore transaction: timeout outcomes remain uncertain and are recovered through stable IDs/current-snapshot replay. No distributed atomicity is claimed.
