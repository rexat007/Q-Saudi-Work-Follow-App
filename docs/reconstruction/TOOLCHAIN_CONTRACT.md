# TOOLCHAIN CONTRACT
## Q-Saudi Work Follow Reconstruction

### Canonical Toolchain Specification
- **Canonical Package Manager**: npm
- **Package Manager Version**: 10.9.8
- **Canonical Lockfile**: `package-lock.json`
- **Supported Node Major Version**: 22
- **Node Engine Constraint**: `>=22 <23`
- **NPM Engine Constraint**: `>=10 <11`
- **Clean Install Command**: `npm ci --no-audit --no-fund`
- **Local Dependency Change Command**: `npm install`
- **CI Install Command**: `npm ci`
- **Alternate Package Manager Lockfiles**: Non-canonical lockfiles (`bun.lock`, `bun.lockb`, `pnpm-lock.yaml`, `yarn.lock`) are strictly non-canonical and must not be committed.

---

### Atomic Dependency Change Boundary
Any dependency change must update:
- `package.json`
- `package-lock.json`

as one atomic implementation unit. A `package.json` dependency change without its corresponding resulting `package-lock.json` change is invalid.

### Lockfile Integrity
`package-lock.json` must be generated by npm. Manual hand-editing of `package-lock.json` is prohibited.

### Dependency Upgrade Discipline
Dependency and package version upgrades must NOT occur incidentally inside unrelated reconstruction units.

Every intentional dependency upgrade requires:
- Explicit unit scope;
- Impact assessment;
- Regenerated canonical lockfile;
- Relevant verification evidence.

### Package Manager Change Control
Changing away from npm requires:
- Explicit architectural decision;
- Reconstruction impact audit;
- Package scripts, CI, and deployment compatibility review;
- Lockfile migration plan;
- User approval.

No unit may silently introduce another package manager or canonical lockfile. Non-canonical lockfiles (`bun.lock`, `bun.lockb`, `pnpm-lock.yaml`, `yarn.lock`) must never be committed.
